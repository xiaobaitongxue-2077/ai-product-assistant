# AI 产品智能助手 · 设计说明

**AI Product Assistant** — 面向销售拜访与客户咨询的检索增强问答工作台

> 把一堆公司产品资料，变成一个「答得出来、还能指出答案出自第几页」的自助问答入口。

## 1. 要解决的问题

销售在客户现场最常卡住的两件事：

1. **资料找不到**：产品参数散在 PDF 手册、Word 方案、Excel 配置表里，现场翻不动。
2. **不敢乱说**：让通用大模型直接答，它会自信地编造参数。在销售场景里，一个编错的数字比「不知道」更致命。

所以这个系统的验收标准不是「答得像人」，而是**「每一句结论都能指出出处」**——答不出来就明确说答不出来。

## 2. 系统架构

```mermaid

    end

        PARSE[文档解析<br/>切片 + 保留位置]
        IDX[FTS5 全文索引]
        AUTH[权限层<br/>三级角色]
        RET[检索与上下文拼装]

    end

    subgraph 前端 · 浏览器
        CHAT[问答界面]

        EXT[扩展工作台<br/>语音 / PPT / 视频预览]
    end

    F1 --> ING
    F2 --> ING
    F3 --> ING
    ING --> PARSE --> IDX
    CHAT --> AUTH --> RET
    IDX --> RET --> LLM --> CITE
    CITE --> STREAM --> CHAT
    CHAT --> EXT
```

### 请求链路

| 步骤 | 做什么 | 为什么在这一层 |
|---|---|---|
| ① 权限判定 | 按当前角色确定可检索的文档集合 | **必须在检索前**，否则无权限内容会进上下文，等于泄露 |
| ② 检索 | FTS5 全文检索，取 Top-K 片段 | 只取片段，不把整篇塞进 prompt |
| ③ 拼装 | 片段 + 位置元信息 + 系统提示 | prompt 里明确要求「只用给定资料回答」 |
| ④ 生成 | 调用 LLM | 流式返回，边生成边展示 |
| ⑤ 引用回填 | 把引用的片段标回「文档名 + 页码/段落」 | 让结论可核查，也让用户知道该去看原文哪一段 |

## 3. 关键设计决策

### 3.1 用 FTS5 全文检索，而不是一上来就上向量库

- **做法**：用 SQLite FTS5 做关键词检索，配合同义词/术语表提升召回。
- **理由**：产品资料的特点是**术语高度精确**——「额定电流 630A」「防护等级 IP54」这类查询，关键词命中的准确率高于语义检索，而且完全可解释（能明确说出命中了哪个词）。更重要的是，FTS5 是 SQLite 内建的，零额外依赖、零向量化成本，导入一份文档立刻可用。
- **代价**：对口语化、同义改写的提问召回不足（比如用户问「这个能不能防雨」，文档里写的是「防护等级 IP54」）。这是这套方案最明确的短板。

### 3.2 引用必须落到「文档 + 位置」，不能只到「文档」

- **做法**：切片时强制保留 `doc_id + page_no + 段落序号`，回答里回填成可点击的引用标记。
- **理由**：只说「来源：《产品手册》」等于没说——手册有八十页。引用要能支撑核查，就必须细到页码。
- **代价**：切片的元数据变重，且不同格式（PDF / DOCX / XLSX）的位置语义不同，需要统一抽象。

### 3.3 SSE 而不是 WebSocket

- **做法**：用 Server-Sent Events 单向推送生成内容。
- **理由**：这个场景只需要「服务端 → 浏览器」的单向流，WebSocket 的双向能力用不上，反而带来连接管理、心跳、重连策略的额外复杂度。SSE 走普通 HTTP，天然穿透代理和网关，断线由浏览器自动重连，实现成本低得多。
- **代价**：无法中途双向交互（比如生成过程中前端实时干预），需要的话得换协议。

### 3.4 权限在检索层做，不在展示层做

- **做法**：三级角色在发起检索时就把文档集合收窄，无权限的文档根本不进候选。
- **理由**：如果只在界面上隐藏，无权限内容依然会进入 LLM 上下文，模型可能把它「说出来」——这是权限系统最典型的漏洞：**你挡住了眼睛，没挡住嘴**。
- **代价**：权限变更后需要让索引侧感知，缓存的检索结果必须失效。

### 3.5 导入去重

- **做法**：导入时计算文档指纹，重复文档不重复建索引。
- **理由**：销售团队会反复上传同一份手册的不同版本，不去重会把索引撑爆，检索时同一段内容重复命中，反而降低答案质量。
- **代价**：需要判断「同名不同版本」是覆盖还是并存，这里做的是并存 + 版本标记。

## 4. 交付内容

| 能力 | 说明 |
|---|---|
| 知识接入 | PDF / DOCX / XLSX 导入、去重、FTS5 全文检索 |
| 问答 | 带来源引用的 LLM 回答，SSE 流式输出 |
| 权限 | 三级角色控制，检索层过滤 |
| 扩展工作台 | 语音、PPT、分阶段视频预览 |
| 质量保障 | 针对解析异常与权限边界补充测试工具与恢复机制 |

**角色**：独立开发（场景调研、检索与问答链路、权限设计、测试工具）。

## 5. 已知限制

- **召回有天花板**：纯关键词检索对口语化提问、同义改写不友好。下一步方向是「FTS5 召回 + 向量召回融合」，但需要先解决向量库的运维成本和切片策略。
- **权限粒度是角色级**：做不到「某一行数据只给某人看」的行级权限。对当前场景够用，但不是通用方案。
- **引用能约束幻觉，不能根除**：模型仍可能在有资料的情况下答错，只是答案可被核查。系统的定位是「降低出错概率 + 让错误可被发现」，不是「保证正确」。
